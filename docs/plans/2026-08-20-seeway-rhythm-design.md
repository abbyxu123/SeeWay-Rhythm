# SeeWay Rhythm 产品与系统设计

日期：2026-08-20

状态：已确认产品方向，待进入实施规划

## 1. 背景

用户目前需要反复手工查看每个时辰的奇门盘，并将盘面压缩成日常可执行建议。SeeWay Rhythm 的第一目标是自动完成这套重复工作，在常亮桌面设备上持续显示当前两小时时段的关键信息，同时允许用户针对具体事项发起专题分析。

第一版只服务单个用户，不为公开发行调整术语或隐藏计算过程。规则严谨度、日常可读性和设备稳定性优先于账户、商业化和社交功能。

## 2. 已确认的产品决策

- 奇门遁甲负责当前时辰和专题问事，是主要判断系统。
- 紫微斗数只提供本命、流年和阶段背景，不强行制造每两小时变化。
- 河图洛书只校验基础数理映射，不作为独立吉凶评分层。
- 日常页面不展示九宫格，只展示有利、不利、方向和建议。
- 后台必须完整保存盘面、用神、规则匹配、冲突处理和来源。
- 用户情绪不参与术数判断，语音模型不得替代规则引擎。
- 第一版本地优先、单用户、断网可降级使用。
- 第二版再面向美国区 iPhone 和 iPad 设计消费级体验。

## 3. 产品范围

### 3.1 V1 包含

- 出生资料和当前地点配置
- 当前、下一时辰自动计算
- 事业、学习、沟通、财务、出行、家庭等分类结论
- 有利方向和回避方向
- 紫微长期背景
- 专题问事与语音输入
- 规则依据与调试页面
- 手工核盘对照记录
- ESP32 常显、缓存和断网降级

### 3.2 V1 不包含

- 多用户账户
- 社区和内容广场
- 在线支付和订阅
- 云端同步
- iOS 客户端
- 医疗诊断、投资指令或安全保证
- 由大语言模型自由生成吉凶

## 4. 硬件判断

目标设备是 Waveshare ESP32-S3-RLCD-4.2，主要资源为 ESP32-S3、16 MB Flash、8 MB PSRAM、300 x 400 单色 RLCD、双麦克风、音频编解码、扬声器接口、RTC、Micro SD、Wi-Fi、BLE 和侧边按键。

### 4.1 适合的工作

- 常亮显示简洁文本和方向图标
- 每分钟局部刷新时间，每个时辰刷新完整内容
- 保持 RTC 时间
- 缓存未来若干时段结果
- 采集语音并播放提示音
- 通过 Wi-Fi 与本地服务交换结构化数据

### 4.2 不适合首版承担的工作

- 大模型推理
- 高质量通用语音识别
- 快速迭代中的完整奇门、紫微规则编辑与调试
- 依赖触摸手势的复杂界面

### 4.3 硬件限制

- 未提供触摸能力，使用 KEY、BOOT 和语音完成交互。
- 屏幕没有背光，暗处可读性依赖环境照明。
- 300 x 400 单色分辨率要求严格控制每页信息量和中文字体资源。
- 首版网络中断时只能使用已缓存结果，不能完成需要服务端语音识别的新问事。

## 5. 交互设计

### 5.1 常显状态

主页面按优先级显示：

1. 当前时段与剩余时间
2. 顺势事项一至两项
3. 留意事项一至两项
4. 有利和回避方向
5. 一句行动建议
6. 下一时段摘要

紫微背景放在第二页或低频轮播页，避免与当前奇门结论竞争视觉注意力。

### 5.2 按键映射草案

- KEY 短按：切换当前、下一时段和紫微背景页面。
- KEY 长按：进入语音问事并开始录音。
- 录音后 KEY 短按：确认识别结果。
- 录音后 KEY 长按：取消并重新录入。
- PWR：保持原有电源职责。
- BOOT：开发阶段不作为主要交互键，避免影响刷机与恢复操作。

### 5.3 问事流程

用户直接说出事项、人物和计划时间。系统先完成语音识别和结构化，再显示类别与摘要供确认。只有缺少会改变用神或目标盘的关键信息时才追问，并且一次只追问一个问题。

结构化问题至少包含：

- `category`：事项类别
- `question_time`：发问时间
- `target_time`：计划执行时间，可为空
- `actors`：涉及人物及关系
- `action`：准备采取的行动
- `goal`：希望判断的目标
- `location`：当前或目标地点，可为空

## 6. 输出契约

设备接收结构化结果，不接收无法审计的自由文本判断。建议结果对象包含：

```json
{
  "period": "13:00-15:00",
  "summary": "适合推进，重要承诺宜稍后确认",
  "favorable": ["沟通", "展示方案"],
  "cautions": ["价格承诺", "临时让步"],
  "supportive_direction": "东南",
  "avoid_direction": "西北",
  "action": "先确认原则，细节改用书面确认",
  "next_period": "下一时段更适合落实细节",
  "evidence_level": "mixed",
  "rule_version": "qimen-0.1.0",
  "evidence_ids": ["QM-DOOR-001", "QM-STEM-014"]
}
```

`evidence_level` 表示规则证据的一致程度，不得呈现为统计意义上的预测准确率。

## 7. 规则系统

规则系统分为五层：

1. 时间与历法层：时区、节气、干支、日界和时辰边界。
2. 奇门排盘层：阴阳遁、局数、九宫、三奇六仪、星门神和值符值使。
3. 专题取用层：根据事项、人物关系和时间范围确定相关用神。
4. 判断层：旺衰、生克、空亡、驿马和组合条件形成结构化证据。
5. 表达层：把证据压缩为固定字段和短句，不修改判断方向。

每条可执行规则必须记录：

- 唯一规则编号
- 来源材料和页码或课程位置
- 适用流派与版本
- 前置条件
- 结论与强度
- 冲突优先级
- 正例、反例和边界测试

## 8. 系统数据流

1. 本地服务读取用户档案、地点、时区和当前时间。
2. 历法层计算当前及未来时段的确定性时间数据。
3. 奇门、紫微和基础映射层分别生成结构化结果。
4. 规则引擎按事项聚合证据并处理冲突。
5. 表达层生成设备可显示的短句和方向。
6. 设备下载、校验并缓存结果。
7. RTC 到达边界时，设备切换到已缓存时段。
8. 网络恢复后刷新缓存和规则版本。

## 9. 错误与降级

- 无网络：显示缓存，并标明最近更新时间。
- RTC 时间异常：不生成新结论，提示重新校时。
- 出生资料不完整：只显示不依赖个人信息的公共时空层。
- 规则冲突：显示“倾向不明确”，保留证据供调试。
- 语音识别置信不足：要求用户确认或重录，不自动推断关键字段。
- 本地服务版本不兼容：继续使用最后一份有效缓存。

## 10. 测试策略

- 历法边界：日界、子时、节气交接、闰月、时区和夏令时。
- 排盘金样：从来源材料和人工核盘建立固定输入输出样例。
- 规则单元测试：每条规则至少有命中、不命中和冲突样例。
- 确定性测试：同一输入和版本重复运行结果完全一致。
- 设备测试：断网、重启、掉电、RTC 偏差、缓存损坏和中文字体显示。
- 长期对照：记录人工判断与程序输出差异，用于修正规则实现，不用于伪造预测准确率。

## 11. V2 方向

美国区消费版保留相同规则核心，重新设计品牌语言、iPhone/iPad 界面、通知、隐私和商业化。产品可描述为受中国传统历法和象征性时序系统启发的个人节律工具，但不隐藏核心体验，也不宣称经过科学验证的预测效果。

首发商业模式优先考虑免费体验加一次性 Pro 解锁。只有在提供跨设备同步、云端语音、持续内容等持续服务后，再考虑订阅。

## 12. 后续决策

- 确认奇门排盘的具体时间口径和节气换局规则。
- 确认个人化判断中年命、日干和专题用神的优先级。
- 确认紫微首版只做到流年，还是加入有可靠来源的流月规则。
- 确认本地服务语言与 ESP32 固件框架。
- 根据实物测试决定缓存周期、刷新频率和电池策略。
